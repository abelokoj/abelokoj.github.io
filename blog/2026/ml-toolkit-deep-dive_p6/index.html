Part 1: scikit-learn for Handwritten Digit Recognition

What scikit-learn is, and why it is usually the appropriate starting point

scikit-learn is Python’s general-purpose classical machine learning library, providing linear models, kernel methods, tree ensembles, clustering, and dimensionality reduction. It also provides a consistent API across all of them and first-class support for the essential parts of a real workflow. These include cross-validation, preprocessing pipelines, hyperparameter search, and evaluation metrics. Given a problem involving structured or tabular data, and a moderate number of samples, scikit-learn is usually the best starting point. This is not necessarily because it is simpler than deep learning, but because it is often the correct tool. This can be seen from our earlier article in this series on tabular data demonstrated directly.

The dataset: UCI Optical Recognition of Handwritten Digits

In this section, we make use of a real-world dataset, namely; 1,797 scanned handwritten digits Each digit has been digitized as an 8×8 grid of integer pixel intensities (0–16). They were originally collected from 43 people in a US Postal Service-adjacent research effort and hosted at the UCI Machine Learning Repository. It is a smaller, cleaner counterpart to the MNIST dataset used in the TensorFlow section below, and it ships bundled with scikit-learn, requiring no download. That property makes it a useful teaching dataset, since every line below can be run immediately.

from sklearn.datasets import load_digits

digits = load_digits()
X, y = digits.data, digits.target       # X: (1797, 64), y: (1797,)
print(f"Dataset shape: {X.shape}")
print(f"Classes: {sorted(set(y))}")
print(f"Class balance: {np.bincount(y)}")

Each of the 64 columns in X is one pixel’s intensity, flattened from the original 8×8 image, so the model never observes the two-dimensional spatial structure directly. That gap is precisely what a convolutional network, covered in the TensorFlow and PyTorch sections, is designed to exploit. The classes are also close to perfectly balanced, at roughly 180 examples of each digit. This is significant because, it makes plain accuracy a trustworthy metric. This is in direct contrast to the imbalanced breast-cancer dataset of the previous article post in this series.

Step 2: Train/test split, should be performed before anything else touches the data

from sklearn.model_selection import train_test_split

X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.2, stratify=y, random_state=42
)
print(f"Train: {X_train.shape[0]}, Test: {X_test.shape[0]}")

Train: 1437, Test: 360

Two details are worthy of note. Getting them wrong is among the most common sources of errors that silently inflate results in machine learning projects:

  • stratify=y ensures the train and test sets preserve the same class proportions as the full dataset. Without it, a random split could, by chance, under-represent a digit such as “8” in the training set; thus, degrading the model’s ability to learn it.
  • The split happens before any preprocessing is fit. Any transformation learned from data, such as the mean and variance of a StandardScaler or the principal components of a PCA, must be fit only on the training set and then applied to the test set, not the reverse. Fitting preprocessing on the full dataset before splitting leaks test-set information into training. This is a silent source of inflated performance report. scikit-learn’s Pipeline object (used below) exists largely to make this easy to get right by construction.

Step 3: Baseline models via cross-validation

Instead of selecting one algorithm by instinct, four genuinely different model families are compared under identical cross-validation conditions. This is the same discipline used in the previous post in this series, now applied to a 10-class instead of a binary problem.

from sklearn.model_selection import StratifiedKFold, cross_val_score
from sklearn.preprocessing import StandardScaler
from sklearn.pipeline import Pipeline
from sklearn.linear_model import LogisticRegression
from sklearn.neighbors import KNeighborsClassifier
from sklearn.svm import SVC
from sklearn.ensemble import RandomForestClassifier

models = {
    "Logistic Regression": Pipeline([
        ("scale", StandardScaler()),
        ("clf", LogisticRegression(max_iter=5000, random_state=42)),
    ]),
    "KNN (k=5)": Pipeline([
        ("scale", StandardScaler()),
        ("clf", KNeighborsClassifier(n_neighbors=5)),
    ]),
    "SVM (RBF)": Pipeline([
        ("scale", StandardScaler()),
        ("clf", SVC(kernel="rbf", random_state=42)),
    ]),
    "Random Forest": Pipeline([
        ("clf", RandomForestClassifier(n_estimators=300, random_state=42)),
    ]),
}

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)
for name, pipe in models.items():
    scores = cross_val_score(pipe, X_train, y_train, cv=cv, scoring="accuracy")
    print(f"{name:22s} {scores.mean():.4f} ± {scores.std():.4f}")

5-fold CV accuracy on training set:

SVM (RBF)              0.9812 ± 0.0061
Random Forest          0.9749 ± 0.0078

Figure 2: Distribution of 5-fold cross-validation accuracy for each model. The RBF-kernel SVM has both the highest mean accuracy and the tightest spread, which indicates it is the model worth tuning further.

In contrast to the linearly separable breast cancer data of the earlier post, the RBF-kernel SVM performs best here compared to plain logistic regression. Pixel-intensity image data is genuinely non-linearly separable in raw pixel space. An example is because a “3” and an “8” are distinguished by a complicated curved decision boundary as opposed to a hyperplane. This precisely demonstrates the structure a kernel method is designed to capture. This is the purpose of running the comparison instead of simply assuming an answer. The appropriate model depends on the structure of the data, and that structure differs from one data set to another.

Step 4: Hyperparameter tuning with GridSearchCV

Having identified the SVM as the strongest candidate, its two key hyperparameters, C (inverse regularization strength) and gamma (kernel bandwidth), are tuned by exhaustive grid search, still using cross-validation so that the test set remains untouched:

from sklearn.model_selection import GridSearchCV

svm_pipe = Pipeline([
    ("scale", StandardScaler()),
    ("clf", SVC(random_state=42)),
])
param_grid = {
    "clf__C": [0.1, 1, 10, 100],
    "clf__gamma": ["scale", 0.001, 0.01, 0.1],
    "clf__kernel": ["rbf"],
}
grid = GridSearchCV(svm_pipe, param_grid, cv=cv, scoring="accuracy", n_jobs=1)
grid.fit(X_train, y_train)
print(f"Best params: {grid.best_params_}")
print(f"Best CV accuracy: {grid.best_score_:.4f}")

Best params: {'clf__C': 1, 'clf__gamma': 'scale', 'clf__kernel': 'rbf'}
Best CV accuracy: 0.9812

The default hyperparameters (C=1, gamma='scale') proved already optimal on this grid. This occurs more often than newcomers expect, and the search is not wasted effort: the adequacy of the defaults is established only after checking, not before. Trusting defaults without verification and grid-searching everything indiscriminately are both weaker practices than checking.

Step 6: Learning curves, and whether more data or a better model is required

A learning curve answers a specific, practical question: if this model is underperforming, would collecting more training data actually help, or is the model itself the bottleneck?

from sklearn.model_selection import learning_curve

train_sizes, train_scores, val_scores = learning_curve(
    grid.best_estimator_, X_train, y_train, cv=cv,
    train_sizes=np.linspace(0.1, 1.0, 8), scoring="accuracy"
)

Figure 4: Learning curve for the tuned SVM. The training score (blue) stays high and roughly flat, while the validation score (orange) climbs steadily and the gap between the two curves narrows as more data is added, without fully closing.

The curves are read as follows. A large, persistent gap between the training and validation curves indicates high variance (overfitting), for which more data or stronger regularization would help. Curves that converge together to a low plateau indicate high bias (underfitting), which calls for a more flexible model rather than more data. Here the gap is narrowing while the validation curve is still climbing at the right edge of the plot, which suggests the model has not yet saturated: additional training data would likely still help, although the returns are visibly diminishing.

scikit-learn: what to take away

  • The estimator API (fit/predict/transform, all composing inside Pipeline) is what makes rigorous comparison across models inexpensive: the four-model comparison above requires a few dozen lines because every model exposes the same interface.
  • Never fit preprocessing before splitting. Pipeline exists to make this hard to get wrong.
  • Cross-validate before touching the test set, for both model selection and hyperparameter tuning. The test set should be used exactly once, at the end.
  • Learning curves establish whether more data or a better model is required, a question worth answering before committing time to collecting more labeled examples.
  • Examine the individual errors, not the aggregate metric alone: the misclassified-digit grid above is more diagnostically useful than the 97.5% figure by itself.

Part 2: XGBoost for California Housing Price Prediction

(Executed and verified. The dataset was reconstructed from an alternate source; see the note at the top of this post for the corresponding methodology.)

What XGBoost is, and its intended use

XGBoost (“Extreme Gradient Boosting”) is a highly optimized implementation of gradient-boosted decision trees, and for several years was close to the standard winning approach in tabular-data machine learning competitions. Where the tree ensembles of scikit-learn (Random Forest, Gradient Boosting) are robust general-purpose implementations, XGBoost adds second-order (Newton-style) gradient boosting, explicit L1 and L2 regularization built into the training objective, native handling of missing values, and a histogram-based split-finding algorithm that makes it substantially faster on large datasets. These differences are treated mathematically in the previous post in this series.

The dataset: California Housing

This section uses the California Housing dataset, comprising 1990 US Census data on median house values across California census block groups, with features including median income, house age, average rooms per household, and geographic coordinates. It is among the most widely used real-world regression benchmarks in the field, having replaced the older and ethically problematic Boston Housing dataset as the standard regression example in scikit-learn, and it ships as a loader directly in scikit-learn:

Step 1: Baseline with a linear model

A baseline should always be established before adopting a more complex model; the discipline of the scikit-learn section above applies here as well:

A plain linear model on this dataset is documented in the literature to achieve approximately R² ≈ 0.60–0.65; the measured value above (R²=0.5871) falls slightly below this range, though close to its lower bound. It captures the broad income-to-price relationship but misses the non-linear, geographic, and interaction effects that account for a meaningful share of the remaining variance. That gap is precisely what a tree-based model is positioned to close, since trees naturally represent non-linear thresholds and interactions, such as high income combined with coastal latitude, without any manual feature engineering.

Step 2: XGBoost with a proper validation split and early stopping

X_tr, X_val, y_tr, y_val = train_test_split(

model = xgb.XGBRegressor(

Early stopping merits precise understanding rather than mere use. XGBoost adds trees one at a time, and each additional tree reduces training error monotonically; beyond some point, however, additional trees begin fitting noise in the training set rather than genuine signal, and validation error begins to rise. Setting early_stopping_rounds=30 instructs XGBoost to halt training if the validation metric has not improved for 30 consecutive rounds, and to retain the model from the best round rather than the final one. This is a direct practical instance of the bias-variance trade-off: monitoring the validation curve is how the point of diminishing, and subsequently negative, returns is identified.

# Plot train vs validation RMSE across boosting rounds
results = model.evals_result()
epochs = len(results["validation_0"]["rmse"])
fig, ax = plt.subplots(figsize=(7.5, 4.5))
ax.plot(range(epochs), results["validation_0"]["rmse"], label="train")
ax.plot(range(epochs), results["validation_1"]["rmse"], label="validation")
ax.axvline(model.best_iteration, color="gray", linestyle="--",
           label=f"best iteration ({model.best_iteration})")
ax.set_xlabel("boosting round")
ax.set_ylabel("RMSE")
ax.set_title("XGBoost training curve: train vs. validation RMSE")
ax.legend()
savefig_all(fig, "xgb_learning_curve_p6")

Figure 7: Train and validation RMSE across 922 boosting rounds, with the best iteration (892) marked. The two curves separate progressively after approximately round 100, at which point additional trees continue to reduce training error while leaving validation error effectively unchanged.

The resulting curve matches the shape documented in the gradient-boosting literature, and is directly analogous to the neural-network training curves in the TensorFlow, Keras, and PyTorch sections below: the training curve decreases smoothly and continues to decrease, while the validation curve decreases initially, flattens around round 100, and remains essentially flat out to the best round, 892. This is precisely the overfitting signature early stopping is designed to detect automatically rather than requiring visual inspection of a plot at every run.

Two features of this curve depart from what a textbook description of early stopping would lead one to expect.

First, the gap between the two curves is substantial by the end of training. Training RMSE falls to approximately 0.19 while validation RMSE settles near 0.44, a ratio of roughly 2.3. A gap of this magnitude is conventionally read as a symptom of overfitting, and in one sense it is: the model has clearly learned structure specific to the training partition that does not transfer. The more useful observation, however, is that the validation curve does not deteriorate as this gap widens. It flattens and remains flat. The model is fitting training-set noise without that noise actively corrupting its predictions on unseen data, which is the behavior the subsample=0.8, colsample_bytree=0.8, and reg_lambda=1.0 regularization settings are intended to produce. Removing those settings would be a useful exercise: the expected consequence is that the validation curve would begin to rise rather than plateau.

Second, and following directly from the above, early stopping halted at iteration 892 out of a permitted 1000 rather than at some far earlier round. Given that validation RMSE was essentially flat from round 100 onward, the marginal value of rounds 100 through 892 was negligible in accuracy terms while costing approximately eight times the training time and producing a model roughly eight times larger. This illustrates a practical limitation of the early_stopping_rounds criterion: it halts when the metric stops improving at all, not when improvement stops being worth its cost. In a production setting where inference latency or model size is constrained, a tolerance-based criterion, halting once improvement over a window falls below some threshold, would deliver nearly identical predictive performance at a small fraction of the model complexity.

Step 3: Hyperparameter tuning via randomized search

A full grid search over the many hyperparameters of XGBoost is often computationally wasteful. RandomizedSearchCV instead samples a fixed number of random combinations, an approach that tends to be considerably more efficient in high-dimensional hyperparameter spaces, a result with established theoretical support (see Bergstra and Bengio, 2012, in the references):

from scipy.stats import uniform, randint

param_dist = {
    "max_depth": randint(3, 10),
    "learning_rate": uniform(0.01, 0.29),
    "subsample": uniform(0.6, 0.4),
    "colsample_bytree": uniform(0.6, 0.4),
    "reg_lambda": uniform(0.0, 5.0),
    "reg_alpha": uniform(0.0, 2.0),
}

search = RandomizedSearchCV(
    xgb.XGBRegressor(n_estimators=300, objective="reg:squarederror", random_state=42),
    param_distributions=param_dist,
    n_iter=40,
    cv=KFold(n_splits=5, shuffle=True, random_state=42),
    scoring="neg_root_mean_squared_error",
    random_state=42,
    n_jobs=-1,
)
search.fit(X_train, y_train)
print(f"Best params: {search.best_params_}")
print(f"Best CV RMSE: {-search.best_score_:.4f}")

Step 4: Feature importance and interpretation

xgb.plot_importance(model, importance_type="gain", max_num_features=8,
                     title="XGBoost feature importance (gain)")
plt.tight_layout()

XGBoost offers three importance types, and these can disagree, sometimes substantially:

  • weight: the number of times a feature is used to split across all trees. This measure is biased toward high-cardinality features that offer many possible split points.
  • gain: the average improvement in the loss function contributed by splits on that feature. This is generally the most informative measure for determining which features drive predictive power, and it is the one used above.
  • cover: the average number of training samples affected by splits on that feature.

Figure 8: Feature importance by average gain across all trees. MedInc dominates, contributing roughly 2.4 times the average gain of the next-ranked feature.

For this dataset, MedInc (median income) is documented in the literature to dominate by gain by a wide margin, which is unsurprising given how directly income determines purchasing power. The measured gains confirm this: MedInc records an average gain of 7.54, against 3.12 for Longitude, 2.71 for Latitude, 2.54 for AveOccup, 2.00 for AveRooms, 1.54 for HouseAge, 0.97 for AveBedrms, and 0.57 for Population.

The ordering below the leading feature carries more information than the leading feature itself. Two observations follow from it.

The first concerns the geographic coordinates. Longitude and Latitude rank second and third, jointly contributing more gain than any single feature other than MedInc. Neither coordinate carries any intrinsic meaning as a predictor of house value; a linear model would extract almost nothing from them, since price is not a monotonic function of either. Their predictive power here derives entirely from the capacity of a tree ensemble to partition the coordinate plane into regions and assign a separate price level to each. In effect, the ensemble reconstructs an implicit map of California property markets from the coordinates alone. This is a concrete instance of the general claim made earlier: the gap between the linear baseline ($R^2 = 0.5871$) and the tuned ensemble ($R^2 = 0.8509$) is attributable to structure of exactly this kind, which a linear functional form cannot represent.

The second concerns Population, which ranks last with a gain of 0.57, approximately one-thirteenth that of MedInc. This is initially counterintuitive, since block-group population might reasonably be expected to carry information about urban density and therefore price. The likely explanation is redundancy rather than irrelevance: AveOccup is computed as population divided by households, so the two features share a common numerator, and AveOccup additionally normalizes for household count. Where two features encode overlapping information, a boosted ensemble will preferentially split on whichever yields the larger loss reduction, and the gain attributable to the other falls accordingly. Low measured gain therefore indicates that a feature adds little beyond what the other features already supply, which is a different claim from the feature being uninformative in isolation. This distinction matters directly for feature-selection decisions: discarding Population on the basis of its low gain would be defensible here, but the same reasoning applied to a feature whose apparent redundancy is an artifact of the particular training sample would not be.

XGBoost: what to take away

  • Early stopping on a held-out validation set is the standard, automatic means of preventing a boosted ensemble from overfitting. The diagnostic is the validation curve turning upward while the training curve continues to fall.
  • RandomizedSearchCV is usually a better use of compute than exhaustive grid search once more than two or three hyperparameters must be tuned simultaneously.
  • Feature importance type matters. gain, weight, and cover can give meaningfully different accounts of the same trained model, so the measure in use should be identified before conclusions are drawn.
  • Compare against a linear baseline first: the size of the gap XGBoost closes over linear regression is itself a useful diagnostic of how much non-linear and interaction structure the data contains.

Why convolutions, mathematically

A Dense layer connects every input pixel to every output unit with an independent weight: for a 28×28 image, that amounts to 784 independent weights per unit in the first layer, with no representation of the fact that nearby pixels are related. A convolutional layer instead slides a small shared filter, for example 3×3, across the image, computing

\[(\text{feature map})_{i,j} = \sigma\!\left(\sum_{u=-1}^{1}\sum_{v=-1}^{1} w_{u,v}\, x_{i+u,\,j+v} + b\right)\]

at every spatial location, using the same weights $w_{u,v}$ everywhere. This weight sharing encodes two assumptions that are true for images and false for the flattened-pixel-vector approach of Part 1: locality (nearby pixels are more related than distant ones) and translation invariance (a “3” remains a “3” whether centered or shifted slightly within the frame). These two inductive biases are precisely why CNNs substantially outperform flat feedforward networks on image data, and why they justify the added architectural complexity.

Writing the training loop by hand with GradientTape 

loss_fn = tf.keras.losses.SparseCategoricalCrossentropy(from_logits=True)
optimizer = tf.keras.optimizers.Adam(learning_rate=1e-3)

train_loss_metric = tf.keras.metrics.Mean()
train_acc_metric = tf.keras.metrics.SparseCategoricalAccuracy()
val_acc_metric = tf.keras.metrics.SparseCategoricalAccuracy()

@tf.function   # compiles this function into a TensorFlow graph for speed
def train_step(x_batch, y_batch):
    with tf.GradientTape() as tape:
        logits = model(x_batch, training=True)
        loss = loss_fn(y_batch, logits)
    grads = tape.gradient(loss, model.trainable_variables)
    optimizer.apply_gradients(zip(grads, model.trainable_variables))
    train_loss_metric.update_state(loss)
    train_acc_metric.update_state(y_batch, logits)
    return loss

@tf.function
def val_step(x_batch, y_batch):
    logits = model(x_batch, training=False)
    val_acc_metric.update_state(y_batch, logits)

history = {"train_loss": [], "train_acc": [], "val_acc": []}
EPOCHS = 10
for epoch in range(EPOCHS):
    train_loss_metric.reset_state()
    train_acc_metric.reset_state()
    for x_batch, y_batch in train_ds:
        train_step(x_batch, y_batch)

    val_acc_metric.reset_state()
    for x_batch, y_batch in test_ds:
        val_step(x_batch, y_batch)

    history["train_loss"].append(float(train_loss_metric.result()))
    history["train_acc"].append(float(train_acc_metric.result()))
    history["val_acc"].append(float(val_acc_metric.result()))
    print(f"Epoch {epoch+1}/{EPOCHS}  "
          f"loss={history['train_loss'][-1]:.4f}  "
          f"train_acc={history['train_acc'][-1]:.4f}  "
          f"val_acc={history['val_acc'][-1]:.4f}")

Each component of this loop performs a specific function, worth stating explicitly since model.fit() would otherwise conceal all of it:

  • tf.GradientTape() records every differentiable operation performed on its watched variables during the forward pass, so that tape.gradient(loss, model.trainable_variables) can compute $\partial \mathcal{L}/\partial \theta$ for every parameter $\theta$ by reverse-mode automatic differentiation: the same backpropagation algorithm derived from first principles, made explicit rather than hidden.
  • from_logits=True on the loss tells TensorFlow the network’s final layer outputs raw, unnormalized scores rather than probabilities, and that the loss function itself should apply the numerically stable combined softmax and cross-entropy computation internally. This is directly analogous to BCEWithLogitsLoss in the PyTorch section below, and for the same numerical-stability reason.
  • @tf.function traces the Python function once and compiles it into a static TensorFlow graph, which then runs considerably faster than eager, line-by-line execution. This accounts for a meaningful share of the production performance advantage of TensorFlow over naive Python loops.
  • Separate train_acc_metric and val_acc_metric objects, each with their own reset_state() per epoch, is the idiomatic TensorFlow pattern for tracking running statistics across a tf.data pipeline: the metrics accumulate over all batches in an epoch, then report a genuine epoch-level average rather than a noisy single-batch value.

The informative quantity to observe is not the final number but the shape of the two curves: training accuracy climbs smoothly across the ten epochs while validation accuracy is already high after the first (98.19%) and rises only marginally thereafter, the CNN-and-MNIST counterpart of the XGBoost overfitting signature of Part 2, the same underlying phenomenon appearing identically across entirely different model families.

Three aspects of this run bear directly on how the curves in Figure 9 should be read.

Validation accuracy exceeds training accuracy for the first seven epochs. This inverts the usual relationship and is initially surprising: at epoch 1 the network records 91.50% on the training set against 98.19% on the held-out set. The explanation is neither an error nor a data leak but an artifact of how the two quantities are computed. Training accuracy is accumulated during the epoch, averaged across every batch as the parameters are still being updated, so it includes the network’s poor performance on the earliest batches, before it had learned much of anything. Validation accuracy is computed after the epoch concludes, using the final parameter values. The training figure is therefore an average over a trajectory, while the validation figure is a snapshot of its endpoint. A second contributing factor is the dropout layer, which is active during training (randomly zeroing 30% of the units in the penultimate layer) and disabled at evaluation, so the network is evaluated in a slightly stronger configuration than the one being scored during training. The curves cross at epoch 8, once the within-epoch parameter change has become small enough that the averaging effect no longer dominates.

Validation accuracy is not monotonic. It peaks at 99.12% (epoch 6), declines to 98.96% (epoch 9), then recovers to 99.15% (epoch 10). These fluctuations span roughly 0.2 percentage points, corresponding to approximately 20 images out of the 10,000-image test set. Such variation should be treated as noise rather than signal: it reflects the stochasticity of minibatch ordering and dropout sampling, not a meaningful difference in model quality between epochs. The practical implication is a caution against over-reading small differences in a validation metric. Selecting epoch 6 over epoch 10 on the basis of a 0.03-point difference, or reporting either as evidence that one configuration surpasses another, would attribute meaning to what is, on this evidence, indistinguishable from sampling variation.

Training loss continues to fall throughout while validation accuracy plateaus. Loss decreases from 0.2807 to 0.0217, a reduction of more than an order of magnitude, over the same interval in which validation accuracy improves by less than one percentage point. The network is therefore becoming steadily more confident in predictions that were already correct, since cross-entropy loss rewards increased probability mass on the true class regardless of whether the argmax was already right. The distinction matters because loss is the quantity being optimized while accuracy is generally the quantity of interest, and the two can diverge substantially. A model whose loss is still falling is not necessarily still improving in any respect that matters for the task.

TensorFlow (low-level API): what to take away

  • GradientTape is the explicit automatic-differentiation mechanism of TensorFlow, and understanding it amounts to understanding what every high-level .fit() call performs internally.
  • Convolutional layers encode locality and translation invariance directly into the architecture, which is why they outperform flattened-pixel dense networks on image data. This is not an opaque performance gain but a direct consequence of a better-matched inductive bias.
  • @tf.function graph compilation accounts for a large share of the production speed advantage of TensorFlow over naive Python, and is worth adopting once prototyping is complete.
  • from_logits=True and computing softmax/cross-entropy together is a numerical-stability pattern that recurs across every deep learning framework, not a TensorFlow-specific quirk.

Two architectural choices worth understanding rather than treating as boilerplate:

  • Embedding(VOCAB_SIZE, 32) replaces the naive approach of one-hot encoding each word (a 10,000-dimensional sparse vector per word) with a learned, dense 32-dimensional representation per word. This run is the most instructive of the four for a reason unrelated to its accuracy: it is the only one in which overfitting is unambiguous rather than merely latent.

Validation loss rises while validation accuracy does not fall. Between epochs 2 and 5, validation loss increases from 0.3062 to 0.4539, an increase of roughly 48%, while validation accuracy remains within a narrow band, moving from 87.70% to 87.44% with an intermediate maximum of 87.72% at epoch 3. Read together, these indicate that the additional training did not change which reviews the model classifies correctly so much as how confidently it commits to its predictions. Because cross-entropy penalizes confident errors far more heavily than tentative ones, a model that becomes increasingly certain about a fixed set of mistakes will register sharply rising loss with an essentially unchanged accuracy. This is precisely why EarlyStopping is configured here to monitor val_loss rather than val_accuracy: loss detected the degradation at epoch 3, whereas accuracy would not have triggered a halt at any point within the twenty permitted epochs.

The reduced learning rate did not arrest the divergence. ReduceLROnPlateau halved the learning rate from $10^{-3}$ to $5 \times 10^{-4}$ after epoch 3, and validation loss nonetheless rose further at epochs 4 and 5. The episode clarifies what a learning-rate schedule can and cannot accomplish. A smaller step size allows the optimizer to settle more precisely into a minimum it is approaching; it does not prevent the optimizer from continuing toward a minimum of the training objective that is displaced from the minimum of the generalization error. The model was not oscillating around a good solution and failing to converge, which is the pathology a schedule addresses. It was converging accurately toward an overfit one.

Training accuracy reaches 97.06% against a validation ceiling near 87.7%. The gap of approximately ten percentage points by epoch 5 quantifies how much of the training set the model has committed to memory rather than generalized from. Given a 10,000-word vocabulary embedded in 32 dimensions and 25,000 training reviews, a model of this capacity can straightforwardly memorize lexical idiosyncrasies specific to individual reviews. The Dropout(0.4) layer and early stopping are the two mechanisms opposing this, and the evidence above indicates that early stopping did the greater share of the work, since dropout alone did not prevent training accuracy from climbing steeply after epoch 2.

Together these observations qualify the accuracy figure itself. The reported 87.46% is the test accuracy of the epoch-2 model, recovered by restore_best_weights=True. Had the final epoch-5 weights been retained instead, as they would have been without that setting, the reported figure would have been drawn from a model with 48% higher validation loss and materially worse calibration, at approximately the same accuracy. The headline metric would have concealed the difference almost entirely.

A second, oppositely valenced example, “an absolutely brilliant and moving film”, was classified as positive with p=0.881. Both hand-written examples were classified correctly, with probabilities well away from the decision boundary in each case.

Testing a trained model on manually written examples of this kind, rather than relying on the aggregate test-set figure alone, is sound practice for detecting failure modes that the specific distribution of the test set may not surface, such as sarcasm, mixed sentiment, or vocabulary outside the top-10,000-word training vocabulary. Keras: what to take away

  • model.fit() performs everything the GradientTape loop of Part 3 does explicitly; the benefit is fewer lines and fewer opportunities for bugs, not different underlying mathematics.
  • Embeddings convert a large, sparse, one-hot vocabulary representation into a small, dense, learned one: the same dimensionality-reduction principle as PCA, but trained end-to-end for the specific task rather than fit to unsupervised variance.
  • LSTMs, and recurrent architectures generally, exist to capture order-dependent and long-range structure in sequences, but are increasingly outperformed by attention-based (transformer) architectures on this class of task, which is worth stating rather than presenting LSTMs as state-of-the-art.
  • Callbacks (EarlyStopping, ReduceLROnPlateau) are the mechanism Keras provides for injecting training-loop logic without writing a manual loop. The built-in callbacks should be learned before a custom training loop is written to implement behavior a callback likely already covers.

(Executed and verified; see the note at the top of this post for the dataset source used.)

What PyTorch is, and how it differs philosophically

PyTorch’s defining design choice is imperative, eager execution: every operation runs immediately, exactly as plain Python/NumPy code would, and the computational graph used for backpropagation is built dynamically on each forward pass rather than defined once in advance. This is a genuine practical difference from the declarative Sequential style of Keras: it makes PyTorch particularly well suited to architectures with data-dependent control flow, such as a variable number of layers depending on the input, recursive structures, or custom training procedures, which accounts substantially for its prevalence in current research code.

Defining the network as an nn.Module subclass

class FashionCNN(nn.Module):
    def __init__(self):
        super().__init__()
        self.conv_block = nn.Sequential(
            nn.Conv2d(1, 32, kernel_size=3, padding=1),
            nn.ReLU(),
            nn.MaxPool2d(2),                      # 28x28 -> 14x14
            nn.Conv2d(32, 64, kernel_size=3, padding=1),
            nn.ReLU(),
            nn.MaxPool2d(2),                      # 14x14 -> 7x7
        )
        self.classifier = nn.Sequential(
            nn.Flatten(),
            nn.Linear(64 * 7 * 7, 128),
            nn.ReLU(),
            nn.Dropout(0.3),
            nn.Linear(128, 10),                   # logits over 10 classes
        )

    def forward(self, x):
        x = self.conv_block(x)
        return self.classifier(x)

model = FashionCNN().to(device)
print(model)

The training loop, written explicitly (PyTorch’s default style)

criterion = nn.CrossEntropyLoss()   # combines log-softmax + NLL loss internally
optimizer = optim.Adam(model.parameters(), lr=1e-3)
scheduler = optim.lr_scheduler.StepLR(optimizer, step_size=5, gamma=0.5)

def train_one_epoch():
    model.train()
    running_loss, correct, total = 0.0, 0, 0
    for images, labels in train_loader:
        images, labels = images.to(device), labels.to(device)

        optimizer.zero_grad()
        outputs = model(images)
        loss = criterion(outputs, labels)
        loss.backward()
        optimizer.step()

        running_loss += loss.item() * images.size(0)
        correct += (outputs.argmax(dim=1) == labels).sum().item()
        total += labels.size(0)
    return running_loss / total, correct / total

@torch.no_grad()
def evaluate(loader):
    model.eval()
    correct, total = 0, 0
    for images, labels in loader:
        images, labels = images.to(device), labels.to(device)
        outputs = model(images)
        correct += (outputs.argmax(dim=1) == labels).sum().item()
        total += labels.size(0)
    return correct / total

EPOCHS = 10
history = {"train_loss": [], "train_acc": [], "test_acc": []}
for epoch in range(EPOCHS):
    train_loss, train_acc = train_one_epoch()
    test_acc = evaluate(test_loader)
    scheduler.step()

    history["train_loss"].append(train_loss)
    history["train_acc"].append(train_acc)

          f"lr={scheduler.get_last_lr()[0]:.5f}")

Every line here is deliberate, and worth being able to explain, since this pattern (or a close variant of it) is what almost every PyTorch training script in the wild looks like:

  • optimizer.zero_grad() must be called explicitly before each backward pass, because PyTorch accumulates gradients into .grad by default rather than overwriting them. This is a deliberate design choice that supports techniques such as gradient accumulation across memory-constrained mini-batches, but it silently corrupts training if the reset is omitted at any step.
  • loss.backward() triggers reverse-mode automatic differentiation through the dynamically-built computational graph from this forward pass, populating .grad on every parameter. It is the direct PyTorch equivalent of tape.gradient(...) in Part 3.
  • @torch.no_grad() on evaluate() disables gradient tracking during inference, which meaningfully reduces memory usage and speeds up the forward pass, since the computational graph need not be retained for a pass on which .backward() will never be called.
  • model.train() / model.eval() toggle layer-specific behavior. Dropout is active during .train() and disabled, passing data through unchanged, during .eval(); BatchNorm layers, which are not used in this particular architecture but are common enough to note, switch between batch statistics and stored running statistics across the two modes. Forgetting to call .eval() before evaluation is one of the most common and hardest-to-notice PyTorch bugs, since the model still runs and produces plausible-looking but silently degraded predictions.
  • StepLR is a manual learning-rate schedule, halving the learning rate every 5 epochs. It is the direct PyTorch analog of ReduceLROnPlateau in Part 4, although specified here on a fixed schedule rather than triggered adaptively by validation performance.

A CNN of this size and shape is widely reported to reach roughly 91–93% test accuracy on Fashion-MNIST, and the measured test accuracy above, 92.40% after 10 epochs, falls within this range. This task is meaningfully harder than plain-digit MNIST, on which the same architecture family reached 99.15% two sections above, since clothing categories such as “shirt”, “pullover”, and “coat” are visually ambiguous even to a human reader at low grayscale resolution. Training accuracy (94.68%) has also drawn visibly ahead of test accuracy by the final epoch, the same overfitting signature observed in the XGBoost and TensorFlow sections above.

The instructive comparison here is with the MNIST run of Part 3, since the two use a near-identical architecture and differ almost entirely in the difficulty of the data.

The accuracy curves cross, and the crossing point is informative. For the first three epochs test accuracy exceeds training accuracy, for the same dropout-and-averaging reasons set out in Part 3. The curves meet at approximately epoch 4, and from that point the gap widens steadily in the opposite direction, reaching 2.28 percentage points by epoch 10. The MNIST run, by contrast, showed the curves crossing only at epoch 8 and separating by roughly 0.16 points thereafter. The same architecture, trained for the same number of epochs with the same optimizer, therefore overfits Fashion-MNIST an order of magnitude more than it overfits MNIST. This is a direct consequence of task difficulty rather than of any modeling choice: where the generalizable signal is weaker, a fixed-capacity model devotes proportionally more of that capacity to memorization.

Test accuracy peaks at epoch 9, not epoch 10. The final epoch records 92.40% against 92.47% at epoch 9, a decline of 0.07 points. As with the corresponding fluctuations in Part 3, a difference of this size, roughly 7 images out of 10,000, should not be over-interpreted. The detail matters chiefly because this run had no EarlyStopping callback: the training loop as written simply executes ten epochs and reports whatever state it arrives at. Had the run continued for a further twenty epochs, the evidence in the figure suggests test accuracy would have continued to flatten while the training curve advanced, and there is no mechanism in this script that would have detected or halted that. The Keras section of Part 4 supplies the missing piece, and the contrast between the two is a fair illustration of what the higher-level API’s callbacks are actually providing.

The learning-rate schedule produced a visible effect. StepLR halved the learning rate after epoch 5 and again after epoch 10. The single largest single-epoch improvement in test accuracy, 0.61 points, occurs between epochs 5 and 6, immediately following the first reduction, and training loss falls by 0.034 across the same interval against 0.024 in the preceding one. This is the behavior a schedule is intended to produce, and it constitutes a useful counterpart to the Keras result of Part 4, in which the reduction was applied too late to be of any assistance. The distinguishing factor is timing relative to the onset of overfitting: reducing the step size while the model is still improving allows finer convergence, whereas reducing it after generalization has begun to degrade merely refines the descent toward a solution that is already overfit.

The individual errors are semantically plausible. In Figure 12, the single misclassification within the displayed batch assigns a sneaker to the “Bag” class. At 28×28 grayscale resolution, a low side-on shoe silhouette and a flat handbag silhouette share a broadly similar outline, and the distinguishing evidence, such as a sole, laces, or a strap, occupies few pixels. The wider point generalizes the corresponding observation from Part 1: inspecting the actual errors is diagnostically more useful than the aggregate figure, because it distinguishes between a model that has failed to learn the task and a model encountering the genuine limits of the input representation. The errors here are of the latter kind, which suggests that improving on 92.40% would require higher-resolution inputs or data augmentation rather than simply a larger network.

PyTorch: what to take away

  • Eager execution means PyTorch code runs and can be debugged with standard Python tools (print, a debugger, stepping line by line) exactly as any other Python program does, requiring no separate graph-compilation model, in contrast to the @tf.function-compiled path of Part 3.
  • optimizer.zero_grad() before every backward pass is not boilerplate to be skimmed: omitting it is a common bug in which gradients silently accumulate across steps.
  • model.train()/model.eval() materially change model behavior through dropout and batch normalization. Always call .eval() before evaluation or inference, and return to .train() before resuming training.
  • The architecture itself is framework-agnostic. The same convolution-pooling-dense structure appears nearly identically in both the TensorFlow and PyTorch sections; what differs is the surrounding ergonomics, not the underlying mathematics.

Every measured value falls within, or immediately adjacent to, the range reported in the literature. This is a modest result, but not a trivial one. It indicates that the architectures and hyperparameters used here are close to their respective published configurations, and that no error in the data pipelines, particularly the two datasets reconstructed from alternate sources as described at the top of this post, has materially distorted the outcome. Had any section deviated substantially from its expected range, the appropriate first inference would have been a defect in the implementation rather than a discovery about the method.

The magnitude of overfitting tracks task difficulty rather than model family. The three deep-learning sections use comparable regularization (dropout at 0.3 to 0.4) and identical optimizers (Adam at $10^{-3}$), yet the train-test gap spans two orders of magnitude across them: 0.16 points on MNIST, 2.28 on Fashion-MNIST, and approximately 10 on IMDB. The ordering corresponds exactly to the difficulty ordering of the three tasks. Where the generalizable structure in the data is abundant relative to model capacity, as with MNIST, the model has little incentive to memorize; where it is scarce relative to capacity, as with IMDB, memorization is the path of least resistance for the optimizer. This suggests treating regularization strength as a function of the task rather than as a per-architecture default, and a corollary follows for practice: the appropriate diagnostic is not whether a train-test gap exists, but whether it is proportionate to the difficulty of what is being learned.

Loss and accuracy diverge in every section, and monitoring the wrong one has consequences. In Part 2, validation RMSE flattened while training RMSE continued to fall. In Part 3, training loss fell by an order of magnitude while validation accuracy moved by less than one percentage point. In Part 4, validation loss rose by 48% while validation accuracy remained effectively constant. This is the single most transferable observation across all four sections: loss is the quantity being optimized and is sensitive to changes in confidence, while accuracy is typically the quantity of interest and is sensitive only to changes in the argmax. Part 4 furnishes the concrete demonstration of why this matters, since an EarlyStopping callback monitoring val_accuracy rather than val_loss would not have halted training at any point in that run.

Early stopping was decisive in one of the four runs and inconsequential in the others. The XGBoost run halted at iteration 892 of 1000, long after the validation curve had flattened, which cost training time without affecting accuracy. The Keras run halted at epoch 5 of 20 and restored weights from epoch 2, which materially changed the reported result. The TensorFlow and PyTorch runs had no early-stopping mechanism at all and simply completed their allotted ten epochs. The relevant lesson is not that early stopping is always necessary but that its value depends on where the run sits relative to the point of divergence: it is essential when the validation metric genuinely deteriorates, and largely decorative when the metric merely plateaus.

Choosing among the five: an updated decision framework

Having now built a complete pipeline in each tool, the practical guidance of the earlier post in this series holds, with additional detail attached to each row from having worked through the mechanics:

Situation Recommended tool Rationale (from the implementations above)
Small-to-medium tabular data, need interpretability scikit-learn Pipeline + cross-validation + feature importance is a few dozen lines, and the digit-classification example showed even a linear baseline can be highly competitive
Larger tabular data, need best-in-class accuracy with less tuning effort XGBoost Second-order boosting + built-in regularization + early stopping closed a real, measurable gap over a linear baseline on California Housing
Image, audio, or other spatial/grid-structured data TensorFlow or PyTorch (CNNs) Convolutional weight-sharing encodes locality and translation invariance directly; a flattened-pixel Dense/Linear layer cannot match this without substantially more data
Sequential/text data with long-range dependencies Keras/TensorFlow or PyTorch (RNNs, or better, attention-based models) LSTMs captured genuine sentiment-flipping structure in the IMDB task, though with a real, honestly-reported accuracy ceiling relative to modern transformer architectures
Need to iterate quickly on standard architectures Keras Sequential/fit() The entire IMDB training loop, comprising data pipeline, model, callbacks, and training, fits in well under 40 lines
Need custom training logic, research-style flexibility PyTorch, or TensorFlow’s low-level GradientTape API Both expose the explicit backward-pass/optimizer-step mechanics directly, at the cost of writing more boilerplate yourself
Deploying to production, mobile, or edge devices TensorFlow (TF Lite, TF Serving) Not demonstrated directly above, but a genuine ecosystem advantage worth knowing about when the project reaches that stage

Summary Notes and Highlights

  • The underlying mathematics is shared far more than the five different APIs make it look. Gradient descent, backpropagation, regularization, and early stopping all appear, in some form, across every section above. A boosted tree ensemble and a bidirectional LSTM address structurally the same kind of problem, namely minimizing a loss over held-out data without overfitting the training set, using substantially different function classes.
  • Start simple, and mean it. Every section here started with a baseline, whether a linear model or a shallow comparison, before adopting the more sophisticated tool; and in the first section, the simplest model available was not outperformed by the more complex ones on that dataset. That pattern is worth adopting as a default workflow rather than treating it as a rhetorical device.
  • Validation curves are the single most-repeated diagnostic across all five tools. Cross-validation folds in scikit-learn, the train/validation RMSE plot in XGBoost, and the train/validation loss-and-accuracy curves in TensorFlow, Keras, and PyTorch all perform the same underlying check: whether the model is learning generalizable structure or memorizing the training set. Learning to read that plot well transfers across every tool in this post.
  • Framework choice is an engineering decision, not a modeling one. Once a CNN has been determined to be necessary, the choice between TensorFlow and PyTorch has almost no effect on what the model can learn. It is a question of ecosystem fit, deployment target, team familiarity, and the relative value placed on declarative concision (Keras) as against explicit control (PyTorch and low-level TensorFlow).
